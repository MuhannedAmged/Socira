# Security model

## Assumptions

- HTTPS in production, `HttpOnly` + `Secure` + `SameSite=Lax` session cookies, 14-day expiry, logout clears the current cookie and revokes that JWT through a `jti` denylist, and a successful password reset revokes every existing session through a per-user session version.
- Attackers can craft requests, replay callbacks, and guess IDs — so every resource is re-resolved server-side and ownership-checked.

## Controls

- **Tenant isolation:** all queries scoped to the session owner. Ownership-filter regression tests cover post destinations, account disconnection, and media deletion; other handlers use the same `{ ownerId: uid }` pattern and are reviewed in the audit coverage log.
- **Sessions:** `AUTH_SECRET` must be ≥ 32 characters; the JWT is verified with an explicit `HS256` allowlist. `src/proxy.ts` cheaply validates the token before any protected route renders and redirects unauthenticated visitors to `/login?next=…`; authentication is never trusted from the proxy alone. Account status, the token's session version, and a `jti` logout denylist are re-checked in every route handler, so suspension, logout, and password-reset revocation take effect immediately instead of waiting for the 14-day token to expire. The denylist entries expire with the token (Mongo TTL index).
- **OAuth:** the Social SDK generates 256-bit state and a PKCE verifier per attempt; the verifier and provider state stay server-side. The callback's `state` is compared in constant time, the attempt is owner-scoped and expires in 10 minutes, code exchange is claimed atomically before any network call, and the exact redirect URI is enforced against an allowlist. Callback-supplied account IDs and tokens are never trusted; discovered accounts must match the stored attempt.
- **Credentials:** AES-256-GCM with a server-only `CREDENTIAL_ENCRYPTION_KEY` that must decode to exactly 32 bytes (a malformed key throws rather than being zero-padded) plus a key version; scopes + revision persisted; refresh is atomic with race protection; revocation prompts reconnect. Tokens never logged or sent to the browser.
- **Passwords:** bcryptjs (cost 12), with registration/reset inputs capped at bcrypt's 72-byte limit so two different long passwords can never authenticate the same account. A missing account is compared against a fixed dummy hash so login timing cannot be used to enumerate registered emails. Resets are random 256-bit tokens, SHA-256 hashed, 30-minute single-use, rate-limited. The reset token is claimed with one atomic `findOneAndUpdate` before hashing, and a successful reset increments the user's session version so every previously issued JWT is rejected. **Reset links are built only from the configured `NEXT_PUBLIC_APP_URL`; the request `Host` is never used.** If that variable is missing (or is not HTTPS in production), the endpoint refuses to send an email rather than guessing an origin. `passwordHash` is `select: false` in the schema, so it is never returned unless a query explicitly opts in.
- **CSRF:** session cookies are `SameSite=Lax`, and every cookie-authenticated state-changing handler additionally rejects a request whose `Origin`/`Referer` is not the app's own origin. In production, only `NEXT_PUBLIC_APP_URL` is accepted as the app origin (a forged `Host` does not widen it). Requests with neither header (cron, native clients) carry no ambient cookie and are unaffected.
- **Email verification:** 6-digit numeric codes, SHA-256 hashed, 15-minute expiry, resend + attempt caps, constant-time compare, neutral responses against enumeration. Attempts are claimed with one conditional `findOneAndUpdate` (`attempts < 6`) and the code is consumed atomically, so concurrent requests cannot exceed the cap or verify twice. When **both** `RESEND_API_KEY` and `RESEND_FROM_EMAIL` are configured, unverified accounts are blocked from product writes (posts, media upload/sign, account disconnect, social connect); without a configured provider the gate stays off to avoid locking users out.
- **Uploads:** private Supabase bucket, user-scoped paths, an app-side MIME allowlist and per-type size caps (25 MB images, 512 MB video), signed URLs, per-user upload rate limit; service-role key server-only; path traversal blocked by filename sanitization. Signed uploads cannot be capped during transfer, so `POST /api/media` fetches the object's server-recorded metadata with `storage.info()` and rejects (and deletes) any object whose real `size` or `contentType` differs from the declared values or whose metadata is missing. The shared rule set lives in `src/lib/media/constraints.ts`; the same allowlist is applied when a signed URL is minted. **Bucket `file_size_limit` and `allowed_mime_types` remain recommended defense-in-depth**, especially for uploads that are never recorded (see the known limits below). Every storage read/delete is restricted to the configured bucket — a bucket value read from a database row is never passed to the service-role client. Assets expire 3 days after upload and are deleted from storage before their database record, so a failed storage call stays retryable. The cleanup endpoint is bearer-only and compares `CRON_SECRET` in constant time.
- **Abuse:** rate limits on auth/verify/reset/media/post/notification writes keyed by network origin *and* by account, so neither a single IP nor a single account can be brute-forced and spoofed forwarding headers do not remove the per-account ceiling. The limiter itself is bounded and sweeps expired entries. The cron endpoint compares `CRON_SECRET` in constant time using equal-length digests; webhooks (where implemented) verify signatures on raw bytes with idempotent processing.
- **Transport/headers:** a per-request Content-Security-Policy generated in `src/proxy.ts`: `script-src` uses a random nonce plus `'strict-dynamic'` (no `'unsafe-inline'`, no arbitrary HTTPS origin, `'unsafe-eval'` only in development), `style-src` keeps `'unsafe-inline'` for inline style attributes, `connect-src` is limited to the app plus the configured Supabase origin, and `frame-ancestors`/`object-src` are `'none'`. `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`, and HSTS in production come from `next.config.ts`. API responses carry `Cache-Control: no-store` so authenticated JSON is not retained by browsers or shared caches. `X-Powered-By` is disabled. Nonce CSP requires dynamic rendering, so all pages are `force-dynamic`.
- **Audit:** workspace deletion purges owned documents and records the deletion event after the purge, so the event survives while user data does not.
- **Errors/logs:** Zod at boundaries, safe client messages, no secrets in logs or API responses.

## Known limits

- The rate limiter is in-memory and therefore per instance; use a shared store for multi-instance deployments.
- `X-Forwarded-For` is caller-controlled unless a trusted proxy overwrites it. The per-account limits bound the impact; set `TRUSTED_PROXY`-style header stripping at the edge for strict IP accounting.
- `unsafe-inline` remains in `style-src` because the app uses inline style attributes (theme/motion). `script-src` is nonce-gated and never contains `'unsafe-inline'`. `img-src`/`media-src` still allow arbitrary HTTPS because platform avatars and media can live on provider CDNs.
- Logout now revokes the current JWT through the `jti` denylist. The revocation write needs MongoDB: if the database is unreachable, the cookie is still cleared but a copied token remains valid until expiry. Tokens issued before `jti` existed cannot be individually revoked; password reset (session version) or `AUTH_SECRET` rotation invalidates them immediately, otherwise they expire within 14 days.
- Post-upload validation verifies `size` and `contentType` before recording an asset, but a signed upload that is never recorded still consumes bucket storage. Set the bucket's `file_size_limit` and `allowed_mime_types` and a lifecycle cleanup policy; abandoned objects are otherwise only removed by provider lifecycle rules, not by the app.
- Email verification is enforced for product writes only when both Resend variables are configured. If the provider is unavailable or misconfigured, unverified users are not blocked (and may not receive codes); if it is configured, unverified users cannot create posts, upload media, disconnect accounts, or start a social connection until they verify.
- Nonce-based CSP forces every page to render dynamically. Ensure the host/CDN does not cache nonce-bearing HTML across requests; dynamic rendering and `no-store` for APIs are not a substitute for an HTML cache policy.
- Workspace deletion (`DELETE /api/auth/me`) requires a valid session but not a fresh password confirmation. A stolen session can therefore delete the workspace; add re-authentication if that risk matters for the deployment.
- Password-reset tokens travel in the URL (standard for email links). The app sends `Referrer-Policy: strict-origin-when-cross-origin`, but hosting/proxy access logs may still record the full URL; redact `token` at the edge if logs are retained.


## Incident handling

Rotate `AUTH_SECRET` (forces logout), `CREDENTIAL_ENCRYPTION_KEY` (bump version, re-encrypt), OAuth client secrets, `CRON_SECRET`, and Supabase keys independently. Audit security-sensitive events in `AuditLog` without secrets.
